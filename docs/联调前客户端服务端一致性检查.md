# 联调前客户端与服务端一致性检查报告

## 检查范围

- **共享类型**：`admiral-types/src/api.rs`
- **服务端**：`admiral-server` 的 API 路由、请求/响应体、错误格式
- **客户端**：`admiral-client` 的 api_client 路径/方法、commands、Tauri 桥、前端 types 与调用

---

## 一、API 路径与方法

| 接口 | 服务端路由 | 客户端路径 | 结论 |
|------|------------|------------|------|
| 注册 | POST /api/v1/auth/register | POST /api/v1/auth/register | 一致 |
| 登录 | POST /api/v1/auth/login | POST /api/v1/auth/login | 一致 |
| 刷新 | POST /api/v1/auth/refresh | POST /api/v1/auth/refresh | 一致 |
| 当前用户 | GET /api/v1/auth/me | GET /api/v1/auth/me | 一致 |
| 许可 | GET /api/v1/auth/license | GET /api/v1/auth/license | 一致 |
| OAuth 发起 | POST /api/v1/oauth/bilibili/initiate | POST /api/v1/oauth/bilibili/initiate | 一致 |
| OAuth 状态 | GET /api/v1/oauth/bilibili/status | GET /api/v1/oauth/bilibili/status | 一致 |
| OAuth 账户列表 | GET /api/v1/oauth/bilibili/accounts?oauth_session_id= | 同左 | 一致 |
| OAuth 绑定 | POST /api/v1/oauth/bilibili/bind-accounts | 同左 | 一致 |
| OAuth 删除会话 | DELETE /api/v1/oauth/bilibili/sessions/:id | 同左 | 一致 |
| MAPI 代理 | POST /api/v1/mapi/proxy | 同左 | 一致 |
| LLM 对话 | POST /api/v1/llm/chat | 同左 | 一致 |

---

## 二、请求/响应类型（admiral-types 与两端使用）

| 类型 | 服务端使用 | 客户端使用 | 结论 |
|------|------------|------------|------|
| RegisterRequest / LoginRequest / RefreshRequest | Json(req) | to_value(req) | 一致 |
| TokenResponse / RefreshResponse / UserInfo / LicenseResponse | 直接返回 | 反序列化 | 一致 |
| InitiateResponse (authorization_url) | 返回 | 使用 | 一致 |
| TokenMeta (id, platform, created_at) | status 返回 Vec | 反序列化 Vec | 一致 |
| BindAccountsRequest (oauth_token_id, account_ids) | Json(req) | to_value(req) | 一致 |
| OAuth 账户列表 | 返回 `{ records, total }` | 现改为 OAuthAccountsResponse 反序列化 | 已统一（见下） |
| MapiProxyRequest | Json(req) | to_value(req) | 一致 |
| LlmChatRequest | Json(req)，服务端固定 model=deepseek-chat | 同类型 | 一致 |

**已做修正**：客户端原先将 OAuth 账户列表解析为 `serde_json::Value`，已改为使用共享类型 `OAuthAccountsResponse`（并为该类型增加 `Deserialize`），与服务端返回的 `{ records, total }` 结构一致。

---

## 三、错误响应格式

- 服务端：`AppError` 映射为 HTTP 状态码 + JSON 体 `{ "code": string, "message": string }`。
- 客户端：`check_response` 解析非 2xx 时读取 `ErrorBody { code, message }`，401 转为 `ApiError::Unauthorized`。
- **结论**：一致。

---

## 四、业务逻辑对应关系

| 场景 | 服务端 | 客户端 | 结论 |
|------|--------|--------|------|
| 注册成功 | 201 + TokenResponse | 保存凭证，返回 TokenResponse | 一致 |
| 登录成功 | 200 + TokenResponse | 保存凭证，返回 TokenResponse | 一致 |
| 刷新 | 仅返回新 access_token，不轮换 refresh_token | 用新 access_token 更新 store，保留原 refresh_token | 一致 |
| me / license 401 | 返回 401 | 用 refresh 重试一次并更新 token | 一致 |
| OAuth 绑定 | 期望 oauth_token_id = TokenMeta.id | 前端用 status 项的 id 作为 oauth_token_id 传 bind | 一致 |
| OAuth 账户列表 | oauth_session_id 即 token_id（与 status 的 id 同义） | loadAccounts(s.id) 传的即 token id | 一致 |
| MAPI / LLM 请求 | 需要 Bearer | 从 CredentialStore 取 access_token 发送 | 一致 |

---

## 五、前端与共享类型

- `ui/src/lib/types.ts` 与 `admiral-types` 的 DTO 对齐：UserInfo、TokenResponse、RefreshResponse、LicenseResponse、TokenMeta、InitiateResponse、BiliAdvertiserRecord、OAuthAccountsResponse。
- `oauth_token_id`：前端以 string (UUID) 传，Tauri 命令内解析为 `uuid::Uuid`，与 BindAccountsRequest 一致。
- MAPI 返回 `(status, Vec<u8>)`，前端为 `[number, number[]]`，用 `Uint8Array(bytes)` 解码；LLM 返回 `Vec<u8>`，前端用 `number[]` + `TextDecoder` 解码。**结论**：一致。

---

## 六、联调阶段已屏蔽/固定项

- **LLM**：仅 DeepSeek deepseek-chat；服务端固定 `model: "deepseek-chat"`，忽略请求中的 model。
- 其他 LLM 厂商在服务端不初始化，客户端仍可传 model/max_tokens，服务端仅使用 messages 与 max_tokens。

---

## 七、小结

- **路径、方法、请求/响应体、错误格式**：客户端与服务端一致。
- **唯一代码改动**：将 OAuth 账户列表在客户端改为使用共享类型 `OAuthAccountsResponse`，并与服务端返回结构保持一致。
- 联调可直接按当前代码进行；若后续开放多 LLM 或变更接口，再同步更新 `admiral-types` 与两端调用即可。
