# Admiral 任务系统实现报告

本文档描述基于 [prd/6th-任务系统.md](../prd/6th-任务系统.md) 与 [.cursor/plans/admiral_task_system_33f57f26.plan.md](../.cursor/plans/admiral_task_system_33f57f26.plan.md) 完成的**任务系统**具体实现，架构参考 OpenClaw 的 Agent 与任务模式。

---

## 一、整体架构

任务系统由六大模块组成：

| 模块 | 位置 | 职责 |
|------|------|------|
| **记忆系统** | 客户端 `agent/memory.rs` | Markdown 文件存储 + SQLite FTS5 混合检索 |
| **知识体系** | 服务端 `service/knowledge_service.rs` + `api/knowledge.rs` | 知识查询 API（当前为桩，可扩展 pgvector） |
| **Skill 工具体系** | 客户端 `skill/` | skill.toml 解析、注册、校验、执行（MAPI/本地） |
| **Agent Runtime** | 客户端 `agent/` | Profile、Context、ReAct 循环、LLM tool_call 全流程 |
| **任务引擎** | 客户端 `task/` | 状态机、DryRun/TestRun/生产执行、调度器 |
| **数据持久化** | 客户端 `db/` | SQLite 表：tasks、task_runs、conversations、memory_entries、logs |

数据流概览：

- **用户消息** → Context Assembler → ReAct Loop（LLM + tool_call）→ Skill Executor（MAPI/本地）→ 结果回传
- **任务创建** → TaskEngine 持久化 → 状态机流转 → DryRun/TestRun/Production 执行
- **定时/心跳** → Scheduler 触发 → Task Executor 按 TaskPlan 执行

## 二、阶段 A：基础类型与数据层

### 2.1 admiral-types

**`crates/admiral-types/src/skill.rs`**

- `SkillCategory`：Semantic / Tools / Mapi
- `RiskLevel`：Low / Medium / High / Critical
- `SkillApi`：method、path、rate_limit（MAPI 用）
- `SkillInputDef`：required / optional 参数名
- `SkillLlmTool`：name、description、parameters_schema（供 LLM function calling）
- `SkillDefinition`：完整技能定义（id、name、category、platform、description、risk、api、input、llm_tool 等）
- `SkillCall`：技能调用（skill_id、params）
- `SkillResult`：执行结果（success、data、error）

**`crates/admiral-types/src/task.rs`**

- `TaskType`：Instant / Cron / Heartbeat
- `TriggerType`：Instant / Cron / Heartbeat
- `TaskStatus`：Draft → Planning → PlanReady → DryRunning → DryRunPassed → TestRunning → TestRunPassed → Deployed → Scheduled / Running → Succeeded / Failed / Paused
- `TaskTrigger`：trigger_type、cron_expression、heartbeat_condition、next_run_at
- `TaskStep`：seq、skill_id、params、depends_on、description
- `TaskPlan`：steps、estimated_duration_secs、risk_level
- `Task`：id、name、description、task_type、status、plan、platform、account_ids、trigger、created_at、updated_at
- `RunType` / `RunStatus` / `StepResult` / `TaskRun`：执行记录与步骤结果

### 2.2 SQLite 迁移

**`crates/admiral-client/src/db/migrations.rs`**

- **tasks**：id、name、description、task_type、status、plan(JSON)、platform、account_ids(JSON)、trigger 相关字段、created_at、updated_at
- **task_runs**：id、task_id、run_type、status、started_at、finished_at、step_results(JSON)、error
- **conversations**：id、task_id、session_id、role、content、tool_calls、tool_result、timestamp
- **memory_entries**：id、key、content、category、source_file、updated_at（供 FTS5 等扩展）
- **memory_fts**：FTS5 虚拟表（若启用）
- **logs**：request_id、task_id、task_run_id、skill_id、level、category、message、details、timestamp、duration_ms、synced
- **config**：key-value 配置表

启动时在 `main.rs` 调用 `db::migrations::run_migrations(&db::models::db_path())` 完成迁移。

### 2.3 数据访问层

**`crates/admiral-client/src/db/models.rs`**

- `admiral_data_dir()` / `db_path()`：数据目录与 DB 路径
- `upsert_task` / `get_task` / `list_tasks`：任务 CRUD
- `list_scheduled_tasks` / `list_heartbeat_tasks`：供 Scheduler 使用
- `insert_task_run`：写入执行记录
- `row_to_task`：将 SQL 行转为 `Task`（含 Uuid、chrono 解析）

### 2.4 记忆文件结构

**`crates/admiral-client/src/agent/memory.rs`**

- 路径约定：`~/.admiral/memory/USER_MEMORY.md`、`memory/daily/YYYY-MM-DD.md`、`memory/tasks/{task_id}/TASK_MEMORY.md`
- `MemoryStore`：`load_user_memory`、`load_task_memory`、`load_daily_memory`、`write_user_memory`、`append_user_memory_line`、`write_task_memory`、`append_daily`
- `search(query)`：基于 SQLite FTS5 的关键词搜索（失败时返回空）
- `ensure_memory_dirs()`：初始化目录结构

## 三、阶段 B：Skill 系统

### 3.1 目录与 skill.toml 格式

Skill 按目录组织，例如：

```
crates/admiral-client/skills/
  mapi/bilibili/get_account_list/skill.toml
  mapi/bilibili/get_account_balance/skill.toml
  tools/excel_export/skill.toml
  semantic/intent_parser/skill.toml
```

`skill.toml` 包含 `[skill]`、`[skill.description]`、`[skill.risk]`、`[skill.api]`（method/path）、`[skill.input]`（required/optional）、`[skill.llm_tool]`（name、description）等节。

### 3.2 Loader（loader.rs）

- `skills_base_dir()`：基于 CARGO_MANIFEST_DIR 或 data dir 解析 skills 根目录
- `load_skill_from_dir(dir)`：解析单目录下 skill.toml（含 endpoint/path 兼容、description short/long）
- `load_all_skills(base)`：递归扫描子目录，返回 `Vec<SkillDefinition>`

### 3.3 Registry（registry.rs）

- `SkillRegistry`：内部 `RwLock<HashMap<String, SkillDefinition>>`
- `load_from_default_dir()`：从默认目录加载并填充
- `get(id)`、`list_ids()`、`list()`：查询接口
- `build_llm_tools()`：生成 OpenAI/Anthropic 兼容的 function 列表（name、description、parameters）

### 3.4 Validator（validator.rs）

- `validate_call(skill, call)`：校验必填参数、MAPI 类 account_id 等，返回 `Result<(), String>`

### 3.5 Executor（executor.rs）

- `SkillExecutor`：持有 `SkillRegistry` + `ApiClient`
- `execute(call, access_token)`：按 category 分发
  - **Mapi**：调用 `api_client.mapi_proxy`（method、path、params 转 query/body）
  - **Tools**：当前返回“未实现”
  - **Semantic**：返回错误

首批 MAPI Skill 定义已放在 `skills/mapi/bilibili/` 等目录，无需改格式即可被加载。

## 四、阶段 C：Agent Runtime

### 4.1 Agent Profile（profile.rs）

- `AgentProfile`：从 `admiral_data_dir()/agent_profile.toml` 加载人格/规则
- 缺省时使用内置默认 profile
- `build_system_prompt()`：生成系统提示文本

### 4.2 Context Assembler（context.rs）

- `Message` / `Session`：与 OpenAI 风格对齐（role、content、tool_calls、tool_call_id 等）
- `ContextAssembler`：`build(session, user_message, knowledge_snippets)` 组装完整上下文
  - System：Profile + User Memory + Task Memory + Knowledge 片段 + Available Tools
  - Messages：历史对话 + 当前用户消息
- 返回 `Vec<serde_json::Value>`（OpenAI messages 格式）供 LLM 调用

### 4.3 MemoryStore 在 Context 中的使用

- User Memory / Task Memory / Daily 由 MemoryStore 读取，注入 system prompt
- 记忆更新（如对话后提取）可在后续迭代中接入

### 4.4 ReAct 循环（runtime.rs）

- `AgentRuntime::new(api_client, skill_registry)`：构造 Runtime，内部创建 SkillExecutor、ContextAssembler 等
- `process_message(session, user_message, access_token)`：
  1. 调用 `api_client.knowledge_query(user_message, top_k)` 获取知识片段（当前服务端为桩，可返回空）
  2. 循环：`context.build` → `api_client.llm_chat` → 解析 `choices[0].message`
  3. 若存在 `tool_calls`：解析 tool name → skill_id，调用 `skill_executor.execute`，将结果以 tool 角色追加到 session.messages
  4. 直至无 tool_calls 或达到 max_turns
- 返回 `AgentResponse { content, tool_calls_used, session }`（Session 可序列化供前端展示）

### 4.5 与 LLM / MAPI 的衔接

- LLM 调用走现有 `api_client.llm_chat`（Bearer 使用传入的 access_token）
- Tool 执行中 MAPI 类 Skill 走 `api_client.mapi_proxy`，与现有 MAPI 代理一致

## 五、阶段 D：任务引擎与 Tauri 桥接

### 5.1 状态机（state_machine.rs）

- `can_transition(from, to, task_type)`：判断是否允许状态转换
- `transition(from, to, task_type)`：返回 `Result<TaskStatus, String>`，合法则返回目标状态

### 5.2 Task Executor（executor.rs）

- `execute_plan(task, run_type, skill_registry, skill_executor, access_token)`：
  - **DryRun**：仅对每步做 `validator::validate_call`，不调用外部 API
  - **TestRun**：仅执行第一步（或按策略缩小范围）
  - **Production**：按 TaskPlan 顺序执行全部步骤
- 返回 `TaskRun`（含 step_results、error），执行前计算好 error 避免 move 后借用

### 5.3 Task Engine（engine.rs）

- `TaskEngine`：持有 `SkillRegistry`、`SkillExecutor`，与 DB 交互
- `create_task`、`save_task`、`get_task`、`list_tasks`、`transition_to`
- `run_dry_run`、`run_test_run`、`run_production`：调用 executor 并写 DB（task_runs）

### 5.4 Scheduler（scheduler.rs）

- `Scheduler`：持有回调 `ScheduleCallback`，`start()` 内按间隔（如 60s）tick
- 从 DB `list_heartbeat_tasks` 取 `next_run_at` 已到的任务并回调
- Cron 与 Heartbeat 的精确 cron 表达式解析可在后续扩展（如 tokio-cron-scheduler）

### 5.5 AppState 与 Tauri 命令

- **AuthContext**：持 `Arc<ApiClient>`，提供 `get_access_token()` 供 agent_chat 等使用
- **AppState**：增加 `task_engine`、`agent_runtime: Arc<RwLock<Option<AgentRuntime>>>`，在 `create_app_state` 中构造并注入
- **commands/task.rs**：`create_task`、`list_tasks`、`get_task`、`update_task_plan`、`transition_task`、`run_dry_run`、`run_test_run`、`run_production`
- **commands/auth.rs**：`AuthContext::get_access_token()` 供 agent 使用
- **tauri_bridge**：注册 `task_create`、`task_list`、`task_get`、`task_run_dry_run`、`task_run_test_run`、`task_run_production`、`agent_chat(message, task_id?)`
- `main.rs` 的 `invoke_handler` 已注册上述命令

## 六、阶段 E：Knowledge RAG 与前端集成

### 6.1 服务端 Knowledge

- **迁移**：`admiral-server/migration/` 下新增 `knowledge_chunks` 表（id、source_file、chunk_index、title、content、metadata、created_at、updated_at），并建 GIN 全文索引（`to_tsvector('simple', content)`）
- **knowledge_service.rs**：`KnowledgeSnippet`；`query(db, query_text, top_k)` 使用 PostgreSQL 全文检索（`plainto_tsquery` + `ts_rank_cd`）返回相关片段；`ingest_from_dir(db, dir)` 扫描目录下 `.md` 文件，按标题/长度切块后写入 `knowledge_chunks`（同文件先删后插）
- **api/knowledge.rs**：`POST /api/v1/knowledge/query`（AuthUser），body `{ query, top_k }`，返回 `{ snippets }`
- **api/admin.rs**：`POST /api/v1/admin/knowledge/ingest`（管理员），可选 body `{ dir }`，默认目录为环境变量 `ADMIRAL_KNOWLEDGE_DIR` 或 `./knowledge`
- 使用说明见 [docs/知识库初始化.md](docs/知识库初始化.md)

### 6.2 客户端调用 RAG

- **api_client.rs**：`knowledge_query(access_token, query, top_k)`，返回 `Vec<KnowledgeSnippet>`
- **agent/runtime.rs**：在 `process_message` 开头用 `access_token` 调用 `knowledge_query(user_message, 5)`，将 snippet 的 content 列表传入 `context.build` 的 `knowledge_snippets`

### 6.3 前端类型与 Tauri 封装

- **lib/types.ts**：Task、TaskType、TaskStatus、TaskPlan、TaskStep、TaskRun、StepResult、AgentResponse、Session 等类型与后端对齐
- **lib/tauri.ts**：`taskCreate`、`taskList`、`taskGet`、`taskRunDryRun`、`taskRunTestRun`、`taskRunProduction`、`agentChat`

### 6.4 前端 Hooks 与页面

- **useTasks**：tasks、loading、error、refresh、createTask、getTask、runDryRun、runTestRun、runProduction
- **useAgent**：chat(message)、loading、error，支持可选 taskId
- **taskStore**：`fetchTasks` 使用 `tauri.taskList()`，`createTask` 使用 `tauri.taskCreate()`，Task 转 TaskMeta 展示
- **HomePage**：使用 `useAgent(null)`，发送消息调用 `agent_chat`，将返回的 `session.messages` 转为 ChatMessage[] 展示，发送中禁用输入
- **TaskDetail**：ConfirmActions 在 dry_run_passed 时调用 `runTestRun`，在 test_run_passed 时调用 `runProduction`，执行后 refresh 列表
- **TaskList**：状态文案与 TaskStatus 对齐（plan_ready、test_running 等）；TaskCreate 仍通过 store.createTask 走真实 API

## 八、后续可扩展项

- **Knowledge RAG 真实实现**：从 `knowledge/` 读 Markdown、分块、写入 `knowledge_chunks`；query 使用 SQL 全文或接入 pgvector + embedding API
- **记忆自动提取**：对话结束后调用 LLM 提取偏好/事实，写回 USER_MEMORY.md 或 TASK_MEMORY.md
- **Cron 精确调度**：使用 `tokio-cron-scheduler` 解析 cron_expression，在 Scheduler 中触发任务
- **Heartbeat 配置 UI**：前端配置 heartbeat.toml（interval、active_hours、suppress_if_no_action），并在应用内启动 Scheduler
- **任务会话绑定**：首页或任务详情页按 task_id 调用 `agent_chat(message, task_id)`，实现“按任务隔离”的对话
